1. Executive Summary

  • Authenticated API calls use a Bearer JWT access token (~30 minutes). Refresh tokens last 30 days and are stored hashed.
  • Clients use a two-step login: POST /api/auth/login-status (identifier) → then either set-initial-password or password login.
  • Username = email for Student / Parent / Teacher / Tutor self-register and directory create (SchoolAdmin / CampusAdmin too). Login lookup order: username → cnic → mobile_number.
  • Self-service registration creates an inactive app_users row + role in app_user_roles + pending rows in app_approval. Scoped SchoolAdmin / CampusAdmin can activate Student/Teacher in scope; PortalAdmin can activate any; no-school / Parent / Tutor → PortalAdmin only. User sets password via set-initial-password (admin never sets the password on approve).
  • Forgot password: enter username (email) → email reset link + pending app_user_password_reset_request + notify role-scoped helpers. First completion wins (email complete or admin/parent clear).
  • Reject is a soft reject (rejected_at + required rejection_reason); unique indexes ignore rejected rows so the person can re-request.
  • Roles live in app_user_roles (multi-role where allowed). Session role is on the JWT and refresh_tokens.active_role — this is the “Current / Acting as” role in UI, not a separate is_active column on app_user_roles. Exclusive (single-role only): Student, PortalAdmin, SchoolAdmin, CampusAdmin. Combinable on one login: Teacher + Parent + Coordinator + Tutor (any subset). Typical cases: Parent+Teacher, Teacher+Tutor, Parent+Tutor, or all four.
  • Users may request Parent, Teacher, Coordinator, or Tutor as an extra role (app_user_role_request, account stays active) or self-remove Parent / Teacher / Coordinator / Tutor when another role remains. Directory companion grants: PortalAdmin owns Tutors list and all Tutor companion grants/removes; School/Campus Admin may grant Teacher↔Coordinator (and related) in scope but must not grant or remove Parent or Tutor on Teachers/Coordinators lists (see §7b and 03_…QA §7b).
  • School/campus change (Teacher / Student / CampusAdmin / Coordinator) locks the account until an allowed admin applies or rejects the request. Parent and Tutor cannot request school/campus change (they are not assigned school/campus). Student reject may optionally leaveWithoutSchool.
  • admin_target and app_users.role columns are dropped / unused.

2. Username & Login Rules

2.1 Username = email

  • Self-service register (Student / Parent / Teacher / Tutor): email is required; username = normalized email.
  • Directory create (Student / Teacher / Parent / Coordinator / Tutor / SchoolAdmin / CampusAdmin): email is required; username = email. Tutors directory create is PortalAdmin-only.
  • Username stays as registered email on activation (no rewrite to CNIC).
  • Mobile and CNIC remain optional contact / alternate login identifiers (mobile not required on register).
  • Student roll number is required only when a school is selected.

2.2 Login identifiers

GetByLoginIdentifierAsync(identifier):
  1. Match app_users.username (usually email)
  2. Else match app_users.cnic
  3. Else match app_users.mobile_number
  Prefer non-rejected rows (PreferActiveRegistrationAsync), then newest Id.
  Clients send the identifier in the username JSON field.

2.3 Uniqueness (soft-reject aware)

CnicExistsAsync / ix_app_users_cnic_activeUnique among non-rejected rows when CNIC set
MobileNumberExistsAsyncExists check skips rejected rows

After first password via set-initial-password, the user is Ready to sign in — there is no additional forced change-password modal for that path. The React force-change modal applies when an existing session has mustChangePassword === true (e.g. admin-driven reset flows).

4. Login, Set Initial Password, Switch Role

4.1 Login flow (clients)

1. User enters username (email) — or CNIC / mobile if those match
2. POST /api/auth/login-status { username }
3. Branch on Status:
     PendingApproval           → show wait message (stay on identifier)
     Rejected                  → show reject message; offer Request Access
     NeedsPasswordSetup        → show set-password step
     LockedPendingSchoolChange → locked UI (React: /account-locked; Mobile: in-login locked step)
     Ready                     → show password step
4a. NeedsPasswordSetup → POST /api/auth/set-initial-password
       → then password login
4b. Ready → POST /api/auth/login { username, password }
       → JWT + refresh + CurrentUser (active role)
       → RecordLogin / last_login_at updated

4.2 Password login gates (API)

  1. GetByLoginIdentifierAsync
  2. EnsureCanLogin() — blocks deleted, rejected, pending, inactive
  3. If NeedsPasswordSetup → error: set password on login screen first
  4. Verify password (PBKDF2)
  5. Issue refresh token for active role + access JWT; update last_login_at

4.3 Set initial password

  • POST /api/auth/set-initial-password — anonymous; requires identifier + new password (min 6 chars).
  • User must be active and NeedsPasswordSetup.
  • Sets password_hash and clears must_change_password (false).

4.4 Multi-role / switch-role / remove-role

Rules are enforced in UserRoleRules (Domain) when adding or removing a role.

RuleDetail
ExclusiveStudent — cannot combine with any other role
ExclusivePortalAdmin — cannot combine with any other role
ExclusiveSchoolAdmin — whole-school admin; separate login (never with other roles)
ExclusiveCampusAdmin — campus admin; separate login (never with other roles)
May combineTeacher, Parent, Coordinator, Tutor — any subset on one account (UserRoleRules)
Self-removeParent, Teacher, Coordinator, or Tutor via DELETE /api/auth/me/roles/{role}; account must keep at least one other role
Directory removeAdmin may remove companion roles only from the current list view; Parent/Tutor companion changes are PortalAdmin-only on Teachers/Coordinators (see §7b.3–7b.4)

Examples allowed: Teacher+Parent; Teacher+Tutor; Parent+Tutor; Teacher+Parent+Coordinator+Tutor.

Examples blocked: Student+anything; PortalAdmin+anything; SchoolAdmin+Teacher; CampusAdmin+Tutor.

  • Roles are stored in app_user_roles only (user_id, role, created_at). There is no is_active flag on role rows.
  • Default login active role = earliest assignment in app_user_roles (by created_at).
  • POST /api/auth/switch-role (JWT) issues a new access + refresh token scoped to the selected role.
  • DELETE /api/auth/me/roles/{role} (JWT) removes Parent, Teacher, Coordinator, or Tutor, then re-issues tokens for a remaining role. Blocked if student groups still reference that user+role; blocked if it is the only role; Tutor remove also blocked while tutor–student links remain.
  • Refresh tokens store active_role; refresh reuses that role for the new access token.
  • Authorization uses the active (session) role only. API CurrentUser.role = session role; CurrentUser.roles = all assignments.
  • UI: React user-menu Acting as segmented toggle when roles.length > 1; Account page shows Current on the session role with Switch / Remove. Mobile Profile role switcher when multi-role (remove / role-request are Web-first).

5. Logout & Token Revoke

  • POST /api/auth/logout — optional body with refresh token. When provided, that token is revoked (hash lookup). Missing token is a no-op success.
  • React AuthProvider.logout and Mobile ApiAuthRepository.logout send the refresh token then clear local session.
  • Also revoke-all for the user on: school/campus change request (lock) and account deactivate — undocumented as “logout” but required for security.

5.1 Forgot password (email + admin/parent clear)

  1. User → POST /api/auth/password-reset/request { username (email) }. Always returns success (no existence leak).
  2. If an eligible active account with a password exists: cancel prior pending resets; create app_user_password_reset_request; email reset link when email is known; notify role-scoped helpers (PasswordResetRequest).
  3. User → POST /api/auth/password-reset/complete { token, newPassword } — set password via emailed link.
  4. Admin or linked Parent → POST /api/auth/password-reset/clear { username } — clear password hash → NeedsPasswordSetup (Web UI).
  5. First completion wins: completing the pending request (email or clear) blocks all further resets for that request.
  6. User → login-status → set-initial-password (after clear) or sign in directly (after email complete).

6. Registration & Pending Detection

6.1 Self-service register

Client → POST /api/auth/register
  → username = email (required)
  → uniqueness among rejected_at IS NULL
  → INSERT app_users (is_active=false, password_hash=null)
  → INSERT app_user_roles (requested role)
  → INSERT app_approval rows for eligible reviewers
  → notify eligible admins (app_notifications, RegistrationRequest)

6.2 Pending detection

  • Domain: User.IsPendingRegistration (inactive + no password + not rejected).
  • Admin list: GET /api/auth/registrations/pending — PortalAdmin / SchoolAdmin / CampusAdmin; scoped by school/campus where applicable; response includes pendingApprovers and currentUserHasApproved.
  • Login: login-status → PendingApproval.
  • Directory-created users are active immediately with no password (NeedsPasswordSetup) and do not use app_approval.

7. Approval Queue & Soft Reject

7.1 Who can act

ActionPortalAdminSchoolAdminCampusAdmin
List pending registrationsYesYes (scoped)Yes (scoped)
Approve + activate (in scope)AnyStudent/Teacher in schoolStudent/Teacher in campus
Activate no-school / Parent / TutorYes onlyNoNo
Soft-rejectYesYes (scoped)Yes (scoped)

7.2 Activation hierarchy

  • PortalAdmin: activate any pending registration (including Parent / Tutor / no-school).
  • SchoolAdmin: activate Student/Teacher for their school (school-only or with campus).
  • CampusAdmin: activate Student/Teacher for their campus.
  • No school on the request (and Parent / Tutor): PortalAdmin only — School/Campus cannot review.
  • Approve request body is empty — no admin password, no academic override payload. Username remains the registered email.
  • UI may show “Approved — awaiting activation” only if a reviewer recorded approval without activating (rare for in-scope School/Campus Student/Teacher). Soft-approve-without-activate is not the normal School/Campus path for in-scope Student/Teacher.

7.3 “Pending with” filter

  • Pending list returns pendingApprovers from ListPendingApproversForUserAsync: queue rows where is_approved IS NULL.
  • If any CampusAdmin has already approved (is_approved = true), pending SchoolAdmin rows are omitted from “Pending with” — CampusAdmin approval covers SchoolAdmin for display (SchoolAdmin is no longer required).
  • Once any authorized admin activates, the request leaves the pending list.

7.4 Soft reject

  • Body: { "reason": "…" } — required, min 10 characters.
  • Sets rejected_at and rejection_reason; keeps user row and approval trail.
  • Rejector’s app_approval marked rejected (reason stored where applicable).
  • login-status → Rejected (message can surface the stored reason). User may submit a new registration (new row).

7b. Additional Role Requests & Remove Role

7b.1 Self-service request (Parent, Teacher, Coordinator, or Tutor)

  • Eligible signed-in users (not Student / PortalAdmin / SchoolAdmin / CampusAdmin) may request the missing Parent, Teacher, Coordinator, or Tutor role via POST /api/auth/me/role-requests.
  • Does not lock the account; existing role(s) stay usable while pending.
  • Teacher request requires school, campus, and teacher code (teacherCode).
  • Coordinator request requires school, campus, and coordinator code (same teacherCode field). When the requester already has school/campus (e.g. Teacher), Web Account locks those fields and only collects the coordinator code — same idea as directory Teacher→Coordinator grant.
  • Parent may include a reason message only (no school/code).
  • Tutor may include a reason message only (no school/code) — same placement model as Parent.
  • Creates app_user_role_request (status pending) and notifies admins (RoleRequest).
  • GET /api/auth/me may include pendingRoleRequest while a request is open.

7b.2 Admin review

  • GET /api/auth/role-requests/pending — PortalAdmin / SchoolAdmin / CampusAdmin (scoped like registrations).
  • POST /api/auth/role-requests/{id}/approve — adds role to app_user_roles immediately; creates Teacher/Parent/Tutor profile row if missing; applies school/campus (+ code) for Teacher and Coordinator.
  • POST /api/auth/role-requests/{id}/reject — body { reason } (min 10 chars).
  • Web UI: /admin/directory/role-requests (filters, bulk approve/reject, details dialog — same pattern as registration approvals).

7b.3 Directory grant (immediate)

PortalAdmin / SchoolAdmin / CampusAdmin grant some companion roles from the directory list overflow (⋯). Create/Edit forms do not offer extra-role checkboxes — grants are list-only.

PortalAdmin-only for Tutor and Parent companions on Teachers/Coordinators: SchoolAdmin and CampusAdmin must not see or call Add Parent / Add Tutor (or Remove Parent / Remove Tutor) on Teachers or Coordinators lists. Parents list companion grants (Teacher/Coordinator/Tutor) and the entire Tutors directory remain PortalAdmin-only for Tutor mutations.

7b.4 Remove role (self-service + directory)

Self-service

  • DELETE /api/auth/me/roles/{role} — remove Parent, Teacher, Coordinator, or Tutor when another role remains.
  • Re-issues tokens for the remaining (or previous) session role.
  • Blocked when student groups still FK-reference (user_id, role); Tutor blocked when tutor_student_relations still link students.
  • Web Account page: Remove action with confirm. Mobile: out of scope (Web only — intentional).

Directory admin remove (companion roles only)

When an account has more than one role, the list ⋯ menu shows Remove … role for companion roles only. Themed confirm: RemoveDirectoryRoleDialog.

8. School / Campus Change Lock

  • Who may request: Teacher, Student, CampusAdmin, Coordinator. Cannot: PortalAdmin, SchoolAdmin, Parent, Tutor.
  • Confirm on Profile → POST /api/auth/me/school-change → pending request with requester_role.
  • Single role (e.g. Teacher only): account is_active=false, all refresh tokens revoked, login-status → LockedPendingSchoolChange. Response isAccountFullyLocked=true; clients sign out and show locked messaging.
  • Multi-role (e.g. Teacher+Parent): account stays active; only the requesting role is locked. Response includes isAccountFullyLocked=false, lockedRole, and continuation accessToken / refreshToken / user for another unlocked role. React and Flutter Mobile apply that session and keep the user signed in; switching back to the locked role is blocked until approve/reject.
  • login-status → LockedPendingSchoolChange only when the whole account is deactivated.
  • Request UI: React /account and Flutter Mobile Profile (eligible active roles).
  • Admin apply / reject queue: Web only — /admin/directory/school-changes. Mobile does not implement the admin school-change queue.

11. JWT, Refresh Tokens, Security

11.1 JWT claims

ClaimSource
sub / userIdapp_users.id
nameapp_users.username
role (also ClaimTypes.Role)Active session role (enum name)
rolesAll assigned roles, comma-separated (from app_user_roles)
permissionsAuthPermissions.ForRole(activeRole), comma-separated
profileIdRole profile id when loaded
schoolId / campusIdUser school/campus

role = active session role; roles = full assignment list. Authorization uses the active role. mustChangePassword is returned on login / me / change-password responses — not as a JWT claim.

11.2 Security

  • Passwords: PBKDF2 via PasswordHasher.
  • Refresh tokens stored as SHA-256 hex only; lifetime 30 days.
  • Access token: Jwt:AccessTokenMinutes (default 30).
  • Login rate limit: 8 requests per 60 seconds.
  • Password-reset request does not reveal whether the identifier exists.
